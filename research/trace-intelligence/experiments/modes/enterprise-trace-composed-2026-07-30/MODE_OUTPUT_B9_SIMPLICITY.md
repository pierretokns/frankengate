# B9 Simplicity / MDL Analysis

## Thesis

The minimum-description-length answer is not a trace observability stack, graph-memory platform, vector database program, or self-improving agent loop. The shortest coherent system that explains the passed evidence and the negative results is:

**one governed canonical evidence plane in PostgreSQL/Aurora, plus typed proposal/release/evaluation/influence records, exact/structured/lexical retrieval first, optional general task-level embeddings, and lossy exports to ATIF/OTel/eval tools.**

This is not "simple" because it omits hard semantics. It is simple because it keeps all load-bearing semantics in one authority: identity, tenant/team/user scope, purpose, classification, policy epoch, valid/system time, deletion, evidence lineage, release state, and influence exposure. Removing those semantics would shorten the code while lengthening every later explanation, exception, security proof, and incident analysis.

The B9 rule: add a database, graph, vector service, custom embedding, LLM judge, memory framework, dreaming job, or skill-learning loop only when it reduces the total description length of the *validated* system: fewer exceptions, fewer unsafe assumptions, fewer manual reviews, and better held-out outcomes under the same authorization/deletion rules.

## Top Findings

1. **§F1 [Kernel Candidate]: The smallest viable architecture is a governed event/evidence authority, not a federation of trace-intelligence products.**
   - **Evidence:** The combined evidence matrix supports a small governed product around personal history, structural review queues, and evidence-linked eval/procedure proposals, while rejecting root-cause automation, automatic memory writes, collaborator matching, and embedding fine-tuning. The canonical projection work shows ATIF loses original event IDs/parents for enterprise fixtures, while OTel/OpenInference round trips preserve operational span topology but not the full authorization/evidence model. The Wisp governed PostgreSQL benchmark shows same-plane RLS before ranking, history, FTS, structural-event, and proposal-query mechanics at local p50s from roughly 1.4 ms to 23.3 ms.
   - **Reasoning chain:** If ATIF and OTel are projections, and PostgreSQL can already host authority, trace, proposal, and retrieval mechanics, then deploying separate Phoenix/Opik/Langfuse/Graphiti/LangMem/vector authorities increases the proof surface without answering more enterprise questions yet.
   - **Deployment severity:** High. A second authority multiplies deletion, stale-policy, cache, and cross-scope leakage paths in an internal multi-tenant system.
   - **Confidence:** High.
   - **So what:** Build one governed PostgreSQL/Aurora kernel first. Every external framework becomes an adapter, experimental arm, or projection until a named kernel failure is proven.

2. **§F2 [Kernel Candidate]: The load-bearing minimum is richer than "just spans" or "just search."**
   - **Evidence:** The README and composition matrix repeatedly distinguish observed events, model-inferred candidates, reviewed immutable releases, harness projections, influenced trajectories, and independent held-out evals. The v2 primitives add credential-only gating, cutoff-safe temporal evidence, query-independent dream release mechanics, and local runtime attestation because the first memory pilot was confounded by visible labels, non-dreaming dream arms, latest-only context retention, incomplete bitemporality, and unattested runtime/source state.
   - **Reasoning chain:** Apparent simplifications such as one `MEMORY.md`, one span tree, one vector per trace, latest-wins memory, or post-filtered ANN erase facts needed to know what the system was allowed to know, who could see it, whether it was stale, and whether it influenced later evidence.
   - **Deployment severity:** High. These are not elegance concerns; they are the difference between evidence and contamination.
   - **Confidence:** High.
   - **So what:** Do not "simplify" away bitemporality, authority envelopes, release state, deletion lineage, or influence receipts. Those tables reduce total complexity by preventing unbounded special cases.

3. **§F3 [Kernel Candidate]: The first product should be private evidence retrieval and review proposals, not enterprise intelligence claims.**
   - **Evidence:** Current evidence supports showing users their own governed history and creating review candidates for repeated friction, evals, and procedures. It does not support skill-gap inference, named similar-worker discovery, automatic memory, root-cause automation, manager dashboards, or model/fine-tune promotion. CodeTraceBench structural selection missed the preregistered +0.15 precision gate, best blind localization did not beat simple reverse chronology, and Nebius cheap friction signals did not beat trace length by a reliable margin.
   - **Reasoning chain:** The simplest defensible product is one that exposes evidence and asks for review before it claims causes or interventions. Any direct jump to "what skill is missing?" or "who should collaborate?" requires labels and causal tests not yet present.
   - **Deployment severity:** High. Wrong enterprise intelligence claims can harm trust, personnel decisions, and adoption even inside authorized scopes.
   - **Confidence:** High.
   - **So what:** Ship user/private history, citations, search, and proposal queues first. Keep enterprise/team outputs aggregated, anonymous, and explicitly hypothesis-grade until prospective validation exists.

4. **§F4 [Hypothesis With Strong Negative Constraints]: General embeddings are a candidate generator; custom embeddings and new vector stores are not justified yet.**
   - **Evidence:** In the local PostgreSQL joint retrieval run, exact pgvector reached Recall@20 of 0.6667 at 3.017 ms p50, while the tested hybrid RRF improved only to 0.6717 at 256.843 ms p50 and was rejected. The CodeTraceBench factorial found structured+dense better than exact on silver labels, but the labels are not human gold and the task does not prove collaboration, skills, or productivity. The domain-adaptive embedding review explicitly gates adaptation on governed labels and frozen failure of exact/FTS/structured/general-hybrid retrieval.
   - **Reasoning chain:** A model or store earns its place only if it answers cases the cheaper authorized query cannot. Today the bottleneck is labels, authority, temporal evidence, and outcome causality, not vector horsepower.
   - **Deployment severity:** Medium-high. Premature vector complexity creates stale-index and ACL failure modes while distracting from labels.
   - **Confidence:** High for "do not launch custom embeddings now"; medium for the eventual best retrieval implementation.
   - **So what:** Keep task/attempt-level general embeddings behind current authorization and deletion epochs. Evaluate VectorChord, pg_textsearch, pgContext, Turbovec, Turbopuffer, Frankensearch, or custom embeddings only after a preregistered Aurora/general-baseline failure.

5. **§F5 [Kernel Candidate]: Memory, dreams, Graphiti, LangMem, MemInsight, Memory Palace, and `MEMORY.md` should collapse into one proposal/release lifecycle.**
   - **Evidence:** The natural memory composition work retained 48/48 revisions with verbatim/bitemporal mechanics, while latest-only retained 20 and overwrote 28; contextual arms caught same-basename/different-project placebos that latest-only failed. The roadmap concludes Dreams, Graphiti, LangMem, MemPalace, ReasoningBank, Hermes, and RL histories should be mechanisms or experimental arms over native records, not production systems. The dream release v2 code provides deterministic release/quarantine primitives but no corrected model benefit yet.
   - **Reasoning chain:** These tools name different parts of the same lifecycle: extract candidates, preserve temporal facts, reason over contradictions, synthesize proposed memories, review them, release them, render them, and measure influence. A separate store for each role creates more truth locations, not more truth.
   - **Deployment severity:** High. Memory is where circular evidence, future leakage, and policy leakage become easiest to hide.
   - **Confidence:** Medium-high. The representation mechanics are strong; utility remains unproven.
   - **So what:** Implement memory as governed candidate/release/influence records. Use Graphiti/LangMem/Dreams as bounded experiments or algorithms, not as live memory authorities.

6. **§F6 [Kernel Candidate]: Skill learning and NL2SQL replay need one narrow causal gauntlet before any self-evolution architecture.**
   - **Evidence:** The NL2SQL capability checkpoint passed 61/61 component tests, but the Defog factorial smoke had all arms solve the same 2/4 tasks and failed the terminal-protocol gate at 25%-50%. The Hermes self-evolution review found invalid baselines and caller/optimizer contract issues, while the stable Hermes patterns are useful for provenance, protected writes, snapshots, and rollback. The NL2SQL assessment recommends a family-disjoint procedure-mining/replay experiment with no-skill, placebo, and frozen reviewed-procedure arms.
   - **Reasoning chain:** NL2SQL is the simplest deep skill domain because tool calls, schema choices, query errors, policy checks, and executable outcomes are observable. But that same observability exposes that current skill-evolution evidence is mechanics, not benefit.
   - **Deployment severity:** High. Direct SKILL.md/MEMORY.md mutation or self-judged skill release would create circular proof and operational risk.
   - **Confidence:** High.
   - **So what:** Build one proposal/replay spine. No automatic skill file edits, no self-judged promotion, and no broad skill taxonomy product until the repaired NL2SQL gauntlet produces held-out lift.

7. **§F7 [Owner-Acknowledged Limitation]: Public histories and current pilots are sufficient for parser/mechanics work, not enterprise population inference.**
   - **Evidence:** Public-native history audits found mirrored, flattened, scrubbed, and merged traces, not an independent cross-user enterprise panel. The full-cohort memory expansion remained concentrated in two source families and failed diversity/power gates. The first 425-call local memory pilot showed no causal memory benefit and had acknowledged scoring/runtime/design confounds.
   - **Reasoning chain:** A public trace can prove that an importer preserves tool-call structure or that a temporal oracle catches leakage. It cannot prove what employees need, who shares work, or which skills are missing in this deployment.
   - **Deployment severity:** Medium-high. The internal setting reduces public privacy risk, but false organizational generalization remains harmful.
   - **Confidence:** High.
   - **So what:** Treat public corpora as fixtures, negative controls, and parser coverage. Require a consented internal cohort with reviewed labels before team/enterprise recommendations.

## Enterprise Questions Answered and Not Answered

| Question | Current answer class | B9 answer |
|---|---:|---|
| What has this user worked on? | Deterministic/mechanics | Answerable for authorized personal history if import, RLS, deletion, and retention pass production gates. |
| Where did the user repeatedly struggle before success? | Hypothesis/review selector | Candidate traces can be selected; the system cannot yet assert cause or skill deficit. |
| What eval should we add? | Proposal | Generate evidence-linked eval proposals; require human approval and changed-system replay. |
| What memory should we write? | Proposal only | Generate cited memory candidates; no automatic memory promotion. |
| What tools, prompts, skills, memories, or models would improve outcomes? | Causal question | Not answerable without controlled exposure and held-out outcomes. NL2SQL is first plausible domain. |
| Who is doing similar work? | Hypothesis with privacy risk | Anonymous/consented patterns only; no named vector-neighbor people finder. |
| What skills are missing by team or person? | Unsafe unless redesigned | Person-level skill-gap inference is not supported. Team-level support opportunities need ontology, labels, and non-punitive review. |
| What enterprise knowledge should become `MEMORY.md`? | Release decision | Only reviewed, scoped, immutable releases with rollback/deletion lineage. |
| Should we fine-tune embeddings or models? | Future statistical/causal question | No. Trigger only after frozen authorized benchmark failure and positive safety/utility proof. |
| Should we move off Aurora? | Future operations question | No current evidence. Trigger only after selective-RLS/latency/delete/failover workload failure after tuning. |

Unsafe or impossible questions in the current evidence state:

- "Which employee is bad at X?"
- "Who should be introduced to whom?" without reciprocal opt-in and human confirmation.
- "What caused this failure?" from trace similarity or a selector score alone.
- "What memory is true?" from an LLM-generated candidate without cited evidence and review.
- "Did this skill/fine-tune help?" using traces influenced by the same artifact as independent validation.

## Empirical Tests and Falsifiers

1. **Aurora/PostgreSQL sufficiency test**
   - **Run:** Production-like workload with concurrent ingest, personal history, FTS, pgvector, proposal queues, deletion/tombstones, policy epoch changes, failover/reconnect, and analytics isolation.
   - **Falsifies PG-first if:** Current-authority recall, p95/p99 latency, deletion closure, failover recovery, or cost fails after partitioning, typed columns, materialized summaries, bounded vector cardinality, and pool tuning.
   - **Consequence:** Move to a different single authority or authorized sidecar pattern only for the failed workload.

2. **Search complexity test**
   - **Run:** Same candidate universe across exact, structured, FTS, trigram, pgvector, hybrid, Frankensearch, VectorChord/pg_textsearch/pgContext if available, and external vector candidates if needed.
   - **Falsifies simple retrieval if:** A more complex lane delivers material human-labeled utility under equal RLS/delete/latency/cost.
   - **Consequence:** Promote only the lane that wins; keep authority in PG.

3. **Embedding adaptation test**
   - **Run:** Frozen, rights-cleared hard slice with human positives/hard negatives split by user/team/time/source family.
   - **Falsifies general embeddings if:** Enterprise-adapted embeddings improve the primary retrieval metric by a preregistered threshold, e.g. +5 absolute Recall@20, without deletion, memorization, latency, or scope regressions.
   - **Consequence:** Train only for that slice and keep dual-read/shadow/rollback.

4. **Memory benefit test**
   - **Run:** Corrected v2 memory replication with blinded labels, real dream arm, cutoff-safe temporal oracle, runtime attestation, stale/contradiction tests, and influenced-trace exclusion.
   - **Falsifies memory utility if:** Released memory does not beat no-memory/current-memory/placebo controls on verified outcomes, or creates stale/anchoring/security regressions.
   - **Consequence:** Keep memory as review-only proposal UX.

5. **Skill/procedure causal test**
   - **Run:** Repaired Defog/NL2SQL family-disjoint factorial: no artifact, length-matched placebo, expert seed, reviewed trace-mined procedure, optional bounded search arm.
   - **Falsifies skill-learning value if:** No held-out lift on semantic correctness plus policy acceptance, or protocol failures exceed gate.
   - **Consequence:** No self-evolution or procedure release beyond manual docs.

6. **Graph necessity test**
   - **Run:** Temporal multi-hop fact/entity benchmark over relational edges, recursive SQL/materialized views, and an ephemeral Graphiti-style graph.
   - **Falsifies relational-first if:** Graph materially improves reviewed answers under equal ACL, deletion, latency, and operations.
   - **Consequence:** Consider graph as derived rebuildable index, not authority.

7. **Cross-user safety/utility test**
   - **Run:** Consented internal cohort with anonymous aggregate suggestions, reciprocal opt-in, minimum cohort sizes, re-identification attacks, and measured downstream utility.
   - **Falsifies cross-user features if:** Privacy controls erase utility, labels are unreliable, or re-identification remains easy.
   - **Consequence:** Restrict to personal/private history and aggregate non-identifying patterns.

## Architecture Consequences

Minimum coherent system:

- **Canonical evidence tables:** trace/event DAG, source import receipt, parent/child edges, tool-call records, observations, outcomes, artifacts, protected object refs.
- **Authority tables:** tenant, subject, team, purpose, classification, policy epoch, role/scope, deletion/tombstone, current-authority view.
- **Temporal tables:** valid time, system/known time, interval uncertainty, contradiction/gap records.
- **Task and attempt tables:** task signature, attempt segment, model/provider/tool/runtime pins, deterministic signals, outcome labels when reviewed.
- **Retrieval:** typed columns and joins first; JSONB for sparse payloads; FTS/trigram/pgvector for candidate generation inside current authority; source citations returned with every answer.
- **Proposal lifecycle:** candidate, review, release, release entry, destination render, rollback, invalidation.
- **Influence lifecycle:** artifact exposure, retrieval/model/index version exposure, controlled arm, exclusion from independent validation.
- **Evaluation/replay:** eval case, assertion, replay manifest, replay attempt, verifier result, sealed input hash, runtime attestation.
- **Projections/adapters:** ATIF, OTel/OpenInference, AgentEvals, Graphiti/LangMem/Dreams/Frankensearch arms receive derived snapshots with loss receipts.

What should not be in the minimum:

- A production Graphiti graph store.
- Phoenix, Opik, or Langfuse as production authorities.
- LangMem or `MEMORY.md` as live memory store.
- A separate vector database or custom embedding pipeline.
- Automatic SKILL.md/MEMORY.md mutation.
- Cross-user people recommendations.
- LLM-judge-only root cause, skill, or memory promotion.

The strongest simplification is **one authority, many disposable projections**.

## Risks Identified

- **Over-simplification risk:** Flattening to spans, vectors, latest memories, or Markdown files erases authority, time, deletion, and influence semantics.
- **Over-building risk:** Deploying every named framework creates duplicated policy planes and stale derived stores before utility is proven.
- **Metric laundering risk:** Selector precision, retrieval recall, terminal task success, and replay pass rates can be mislabeled as skill, cause, or productivity.
- **Circular evidence risk:** Released memories/skills/retrieval changes alter future traces that later appear to validate the release.
- **Cross-user surveillance risk:** Similarity and skill-support features can become people analytics.
- **External-validity risk:** Public traces are mechanically valuable but demographically and organizationally weak.
- **Runtime/protocol risk:** The invalid first memory pilot and failed Defog protocol show that unsealed mechanics can dominate apparent results.
- **Aurora dogma risk:** PG-first is supported now, but it must remain falsifiable under production workload.

## Recommendations

1. **Adopt the one-authority kernel as the only production architecture until a named gate fails.**
2. **Create a complexity budget:** each new service/model/framework must name the current query it answers, the simpler baseline it beats, the proof it preserves, and the rollback path.
3. **Make claim class explicit in product and storage:** deterministic fact, statistical association, review candidate, causal intervention result, unsafe question, or unsupported claim.
4. **Finish the corrected v2 memory experiment before building memory UX beyond proposals.**
5. **Repair the NL2SQL protocol and run the family-disjoint causal gauntlet before skill-learning release work.**
6. **Run Aurora/selective-RLS/delete/failover load tests before introducing sidecar search as anything more than an experiment.**
7. **Keep embeddings general and task-level until a frozen hard slice proves adaptation is worth the governance burden.**
8. **For cross-user/team features, start with aggregate support opportunities and opt-in artifacts, not named matches.**

## New Ideas and Extensions

- **MDL ledger:** For every proposed component, record "bytes of system complexity added" qualitatively: new authority, new cache, new deletion path, new model, new reviewer surface, new rollback path. Approve only if it removes more complexity from validated workflows.
- **Negative-results registry:** Keep failed gates such as Defog P0 protocol failure, latest-only memory overwrite, hybrid latency rejection, and no-memory scoring artifact visible in release planning.
- **Current-authority oracle:** A shared test harness that asks every projection/index/cache/search arm: "Would this answer be visible now, for this subject, purpose, classification, and epoch?"
- **Influence quarantine by default:** Any trace exposed to an artifact/version is flagged as ineligible for independent validation of that artifact unless the analysis explicitly models exposure.
- **Two-lane UI language:** "Evidence" for deterministic authorized facts; "Candidates" for model/signal output. Never "insights" unless the claim class is proven.
- **Framework adapter kill switch:** Every experimental adapter must be deletable without deleting canonical evidence or losing product behavior.

## Assumptions Ledger

- Internal enterprise users with appropriate authority may see full PII/classified content; ordinary trace research excludes credentials, not all sensitive content.
- Several hundred GB of initial traces does not, by itself, justify leaving Aurora/PostgreSQL.
- Existing local evidence documents are accepted as primary project evidence for this pane.
- Public histories are rights/format/mechanics sources, not valid enterprise population samples.
- The first useful product can be evidence/review/proposal oriented rather than fully automated.
- Query quality, memory utility, skill benefit, and model/embedding benefit are separate claims.
- Human review capacity exists for early proposal queues and label creation.

## Points of Uncertainty

- Aurora behavior under selective-RLS, vector/FTS, deletion, failover, and concurrent analytics has not been proven at production scale.
- The corrected v2 memory primitives look materially better, but no corrected model utility result exists yet.
- Human reliability for labels such as "same work," "repeated friction," "missing skill," and "useful procedure" is unknown.
- General embeddings may underperform enterprise jargon more than current public/silver tests show.
- Frankensearch or PostgreSQL extensions may beat base PG on real workloads, but the security and operations cost is unmeasured.
- NL2SQL may be the best first causal domain, but its gains may not transfer to general coding/research work.
- The optimal balance between user-private history value and enterprise aggregation value remains a product question, not only an architecture question.

- **Agreement with F1 Causal Inference:** Memory, skill, prompt, routing, model, and embedding improvements require exposure/control and independent held-out outcomes. B9 uses that as a reason to avoid building intervention loops until the causal harness is small and working.
- **Tension with F7 Systems Thinking:** F7 is likely to value explicit feedback loops among memory, skills, evals, retrieval, and governance. B9 treats each loop as expensive until influence quarantine and deletion closure are proven.
- **Tension with G6 Multi-Criteria Decision:** Weighted matrices can make many partially useful components look jointly attractive. B9 asks for a harsher rule: if two components answer the same question, keep the one with fewer authorities unless the other wins a frozen benchmark.
- **Agreement with H2 Adversarial Review:** Duplicate stores, post-filtered retrieval, automatic memory, and cross-user similarity are attack surfaces as well as complexity costs.
- **Agreement with I4 Perspective-Taking:** Contestability, opt-in, and non-punitive framing are not extra UX polish. For people-facing claims, they are load-bearing evidence controls.
- **Agreement with A1 Deductive Inference:** The program should enforce type boundaries: projection is not evidence, candidate is not release, similarity is not identity, and association is not cause.
- **Agreement with K2 Scientific:** Every advanced concept can remain in the research program as a falsifiable arm; it should not become production architecture until it beats the minimal baseline.

## Confidence

Overall confidence: **0.87**.

Confidence is high that the current evidence supports a one-authority, proposal-first architecture and does not support production graph memory, automatic memory writes, self-evolving skills, named collaborator matching, root-cause automation, custom embeddings, or a second vector/search authority. Confidence is lower about the eventual retrieval substrate and memory/skill utility because production Aurora gates, human enterprise labels, corrected v2 memory model results, and repaired NL2SQL causal replay remain unrun.
