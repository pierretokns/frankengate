---
title: "Enterprise delegated credentials"
description: "Security contract for token pass-through and token exchange"
---

Frankengate treats delegated credentials as an explicit, per-destination capability. Existing MCP OAuth, per-user OAuth, and per-user header flows remain unchanged unless an operator enables a delegated-credential profile. The current implementation supports direct RFC 8693 subject-token exchange and RFC 7523 JWT-bearer adapter profiles for downstream HTTP MCP clients; the two-leg ID-JAG redemption flow remains a separate profile because its identity provider and resource authorization server have distinct endpoints and bindings.

## Trust boundaries

The inbound bearer, virtual key, session, MCP connection, A2A Agent Card, task, exchange server, and destination service are separate security principals. A credential is eligible for forwarding only after the inbound request has been authenticated by Frankengate and the destination policy has selected the credential source. A virtual key authenticates access to Frankengate; it is never itself a subject token for a downstream exchange.

The exchange server is an explicit egress destination. Its URL must use HTTPS, pass the configured host/domain policy, and accept no redirects. The destination request is separately policy checked. Shared MCP connections cannot carry caller-specific credentials; caller-bound exchange therefore requires per-request credential resolution. Configure the trusted JWT/OIDC identity middleware first; the exchange profile refuses requests without a validated authorization principal.

## Safe defaults and failure behavior

- Pass-through and exchange are disabled by default.
- `Authorization`, `Cookie`, virtual-key headers, and internal `x-bf-*` headers are never forwarded by an implicit rule.
- Only an explicit header allowlist or declared Agent Card security scheme can select a credential.
- Exchange failures, malformed responses, expired credentials, endpoint-policy failures, and cancellation fail closed. Frankengate never falls back to the original bearer after an enabled exchange fails.
- Tokens, assertions, client secrets, private keys, and cache values are absent from logs, traces, errors, metrics labels, persisted configuration, and cache keys. Diagnostics report identifiers, policy decisions, and hashes only.
- Exchange responses have bounded body size, timeout, cache entries, and TTL. Token lifetime is capped by the subject-token expiry when it is available.

Every accepted, denied, exchanged, expired, or failed decision emits an audit event containing request ID, tenant/virtual-key ID, destination ID, auth profile ID, grant/profile, result, reason code, and latency. It does not contain credential material.

## Approved client authentication profiles

The initial implementation supports `client_secret_basic` and `client_secret_post`, selected explicitly per profile. `client_secret_post` is retained for providers that require it; `client_secret_basic` is preferred. `private_key_jwt`, mTLS, and Entra-specific OBO are separate profiles and remain disabled until a key-provider, rotation, algorithm, replay, and tenant-isolation implementation is enabled.

JWT bearer and ID-JAG assertions must use an approved signing key reference, an allowlisted algorithm, a bounded clock-skew window, a unique `jti`, and an audience that exactly matches the configured authorization server. Raw key material is never accepted in ordinary config or emitted by management APIs.

## Credential precedence

For MCP, the selected per-user OAuth/header credential is considered first. An explicit exchange profile may transform that subject for the configured destination. Static server credentials are used only for profiles that explicitly select them. For A2A, the Agent Card security scheme and destination policy must agree; a card cannot grant permission to forward a credential on its own.

For all paths, the selected credential is scoped to the destination, tenant, task/request, and configured audience/resource/scope. A credential selected for one destination is not reusable for another destination unless the exchange policy explicitly names both.

## References

This contract borrows the audience/resource binding and no-token-forwarding requirements from the [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization), the two-stage enterprise-managed authorization model from [MCP Enterprise-Managed Authorization](https://github.com/modelcontextprotocol/ext-auth/blob/main/specification/stable/enterprise-managed-authorization.mdx), and cache/single-flight/negative-failure guidance from [IBM ContextForge's OAuth design](https://github.com/IBM/mcp-context-forge/blob/main/docs/docs/architecture/oauth-design.md). Okta's concrete user-context exchange parameters are documented in [Okta Token Exchange](https://developer.okta.com/docs/guides/set-up-token-exchange/-/main/). The implementation does not forward an inbound Okta bearer to the MCP resource server; it sends only the exchange result.

## Rollback

Disabling the profile immediately stops new exchanges; cached values are bounded by the configured TTL and are not used while the profile is disabled. Legacy MCP and A2A routes continue using their pre-existing authentication behavior. Operators can roll back by disabling the profile without deleting the source OAuth or header configuration.
